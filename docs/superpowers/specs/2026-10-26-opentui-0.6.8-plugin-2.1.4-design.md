# OpenTUI 0.6.8 + @opencode/plugin 2.1.4 upgrade — design

Resolves [#11](https://github.com/canonical/model-compare-opencode-plugin/issues/11),
the `@opencode/plugin` 2.1.4 bump that Dependabot PR #8 could not land.
OpenTUI 0.7.0 is tracked separately in [#13](https://github.com/canonical/model-compare-opencode-plugin/issues/13).

## Intent and why

`@opencode/plugin` 2.1.x requires `@opentui/core` and `@opentui/solid` `>=0.6.6`,
and 2.1.4 wants `>=0.6.8`. This repo pins both at `0.5.17` and declares peers of
`^0.5.8`, so `npm ci` on PR #8 failed with `ERESOLVE` before any test ran. The
same peer range means a host already on OpenTUI `0.6.8` cannot install the
current plugin either: `^0.5.8` rejects `0.6.8`.

The pins exist because the TUI loads inside the OpenCode host, which rewrites the
bare `solid-js`, `@opentui/*` and `@opencode/plugin/tui` imports to its own
modules. The devDependency pins keep the build transform and the types in
lockstep with the host; they are not a runtime dependency of the published
artifact.

The `0.5.17` and `0.6.8` build transforms are byte-identical (verified: same
`@babel/core` 7.29.7, `babel-preset-solid` 1.9.12, `@babel/preset-typescript`
7.27.1, `babel-plugin-module-resolver` 5.0.2, and a byte-identical
`dist/tui.js`), so this upgrade does not change build output. The driver is
dependency resolution and the host type contract, not the renderer pipeline.

## Goals

- Stage 1: `@opentui/core` and `@opentui/solid` devDependencies at `0.6.8`;
  peer ranges widened to `>=0.5.8 <0.7.0` so hosts on `0.5.x` keep working and
  hosts on `0.6.8` start working. `@opencode/plugin` stays at `2.0.32`.
  Full suite, `tsc`, `build-tui` and `pack-smoke` green.
- Stage 2: `@opencode/plugin` at `2.1.4`, `@opencode/theme` added as a
  devDependency at `2.1.4`, peers narrowed to `^0.6.8`, and the `StatusLine`
  colour type corrected. `zod` stays absent, the suite stays green, and #11
  closes.
- The `seroval` override and `tests/unit/dependency-pin.test.mjs` stay unchanged
  and passing in both stages.
- The TUI renders and its keys work against a real OpenCode 2.1.4 host, installed
  explicitly for the smoke run.

## Non-goals

- OpenTUI `0.7.0`. It shipped on 2026-10-25 with a native ABI change, lazy
  Textarea layout, and renderable hooks read from the class at construction
  (reflection-added hooks now need `refreshHooks()`); no plugin release asks for
  it. Tracked in #13, and excluded from the stage-2 peer range on purpose.
- Adopting new OpenTUI features, restyling the TUI, or changing ranking and
  steering behaviour.
- Bumping `@opencode/theme` or any other `@opencode/*` package beyond what
  `@opencode/plugin@2.1.4` pulls in transitively.
- Changing the plugin's `PluginCtx` cast or refactoring the SDK integration. The
  plan's Task 3 checks that the used declarations still exist; a compile-time
  assignability check is a possible follow-up, not part of this upgrade.

## Constraints

- `@opentui/solid@0.6.8` still ships `scripts/solid-transform.js` and still pins
  `solid-js` at exactly `1.9.12` (verified by unpacking the tarball). The exact
  `1.9.12` peer is part of OpenTUI's contract; the plugin's `^1.9.0` works only
  because the host provides `1.9.12`.
- `@opentui/core@0.6.8` peers on `web-tree-sitter@0.25.10` (the same peer exists
  in `0.5.17`, so this is not new) and declares `engines.node >=26.4.0` and
  `engines.bun >=1.3.14`. CI runs Node 20, so `npm ci` prints `EBADENGINE` for
  `@opentui/core` (and `undici@8.12.3` wants Node `>=22.19.0`). Both are
  dev-tree warnings: the host runs Bun and the package declares
  `engines.node >=20`.
- `@opencode/theme@2.0.32` hard-depends on `@opentui/core@0.5.17`, while
  `@opencode/theme@2.1.4` depends on `0.6.8`. The theme can therefore only be a
  devDependency in stage 2. Until then `context.theme` stays untyped (`any`), so
  the theme contract is not type-checked in stage 1.
- The plugin does not read any field that OpenCode 2.1.0 renamed: no
  `providerState`, `resultState`, `providerContext`, `session.compacted`,
  credential `configuration` or compaction `recent`. It uses `http.request`,
  `ctx.agent.get` and RPC commands. `tsc` does not prove this, because
  `src/index.ts` casts `ctx` to `PluginCtx`; the evidence is a diff of the
  `@opencode/plugin` 2.0.32 and 2.1.4 type surfaces plus the greps.
- The OpenTUI 0.6.x breaking surface is not used: no `getLayoutNode()`, no
  nullish layout writes, no `customBorderChars`, no Textarea/Input internals.
  The used surface is `TextAttributes`, `RGBA`, `ScrollBoxRenderable`, the Solid
  `JSX` types, and the renderer API (`on("frame")`, `on("resize")`,
  `requestRender`, `width`, `height`). `tests/unit/tui.test.ts` mocks the
  renderer and the scrollbox geometry, so runtime behaviour is covered only by
  the manual smoke run.
- The integration suite spawns `opencode` from `PATH` and never imports or
  renders `src/tui.tsx`. It is a server-side, version-agnostic gate, not a 2.1.x
  TUI gate. The TUI smoke needs a host installed at the version under test.
- The integration suite boots a real OpenCode binary and does not run in CI, so
  it is a local gate rather than a CI gate.

## Approaches

A. One PR with both bumps. Rejected: mixes the peer-range widening with the SDK
   contract bump, and a failure gives no clue which side caused it.

B. Two staged PRs (chosen). Stage 1 widens the peers and moves OpenTUI while the
   plugin stays put; stage 2 moves the plugin and narrows the peers. Stage 1 is
   independently mergeable and fixes installability on `0.6.8` hosts; stage 2
   carries the contract change. Each stage is verifiable and bisectable.

C. Defer until the host stops moving. Rejected: the drift only grows, and
   `@opencode/plugin` 2.1.x stays unresolvable.

## Decisions

- Target `0.6.8`, the exact version the 2.1.4 host pins, rather than the minimum
  `0.6.6` or the newer `0.7.0`.
- Stage 1 peers: `>=0.5.8 <0.7.0`. This keeps existing `0.5.x` hosts installable
  and admits `0.6.8`; it deliberately does not claim `0.7.0`. The `0.5.8` floor
  is inherited from the previous `^0.5.8`: a `0.5.8`-`0.5.16` host installs but
  sees the `@opencode/plugin@2.0.32` `peerOptional` warning (that package peers
  on `>=0.5.17`), and the `0.6.0`-`0.6.7` band is admitted but untested. Narrowing
  the floor to `0.5.17` would turn that warning into `ERESOLVE`, so the range
  stays wide.
- Stage 2 peers: `^0.6.8`. This deviates from `@opencode/plugin@2.1.4`'s
  open-ended `>=0.6.8` on purpose: an open floor would claim the untested `0.7.0`
  renderer. #13 widens the range when that upgrade happens.
- The theme devDependency and the `StatusLine` fix land in stage 2, when
  `@opencode/theme@2.1.4` aligns with OpenTUI `0.6.8`. The fix is
  `fg?: ColorInput` (or `RGBA | string`) instead of `fg?: string`, because
  `context.theme.text.base` is an `RGBA`.
- Both stages merge to `main` without a version bump. One release follows stage 2
  as `0.5.0` (minor: peer floor and dependency generation), following the repo's
  release-commit convention. If stage 1 needs to ship earlier, it would also be a
  minor release.
- Stage 1 carries this design note and the implementation plan; stage 2 links back
  to them rather than duplicating them.

## Left to the builder

- Any further `src/tui.tsx` type adjustment that `tsc` demands once the theme is
  installed. The known one is the `StatusLine` colour type.
- Whether the integration suite needs a fresh scratch home for the 2.1.x host.
- Lockfile churn. Stage 1: `@opentui/core` and `@opentui/solid` 0.5.17 -> 0.6.8,
  the eight `@opentui/core-*` platform packages, and the removal of the nested
  `@opentui/core/node_modules/strip-ansi`; `web-tree-sitter` stays at 0.25.10.
  Stage 2: `@opencode/*` 2.0.32 -> 2.1.4, the added `@opencode/theme`, and
  `@smithy/*`, `@aws-sdk/*`, `bin-links` and `bowser` transitive moves. Confirm
  nothing else moves.
- Whether to bump CI to Node 22 for the `undici` engine warning, or leave the
  dev-only `EBADENGINE` warnings documented.

## Verification per stage

Both stages: `npm ci`, `npx vitest run tests/unit tests/conformance`,
`npx tsc --noEmit`, `node scripts/build-tui.mjs`, `node scripts/pack-smoke.mjs`,
and the local integration suite.

Stage 1 additionally gets a manual TUI smoke run against an explicitly installed
OpenCode 2.1.x host. Stage 2 repeats it against 2.1.4 and confirms the theme
renders with the corrected `StatusLine` type. If either stage is released, the
release workflow's extra gates (`npm test`, `npm run build`, `npm run typecheck`,
`node scripts/pack-smoke.mjs`, live-remote canary) apply as well.
