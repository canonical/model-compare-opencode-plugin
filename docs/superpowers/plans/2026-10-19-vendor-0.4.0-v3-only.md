# Vendor 0.4.0 — v3-only contract Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Accept upstream schema v3 only (v2 fallback not desired in this plugin version), gated on the live remote serving v3 at release time; no change in what we show.

**Architecture:** The vendored upstream script already emits v3 (`vendor/model_compare.py` @ 0.4.0, verified live: `schema_version: 3`, 71 models). The plugin's contract gate, its fixtures, its canary and the offline fallback stamp still pin v2. Flip every pin to 3 atomically: gate (`validateCatalog`), fallback stamp (`validateStoredCatalog` rebuild), canary `EXPECTED_SCHEMA_VERSION`, harness stub, fixtures. Record one v3 contract fixture (`fixtures/catalog-v0.4.0.json`) + regenerate the no-quality fixture from it; delete the v2 fixture. `make test` + `make e2e` green, then a release gate script step that refuses to release unless the live remote serves v3.

**Tech Stack:** TypeScript (plugin, Bun test), Python (vendored script), Node (`scripts/*.mjs` harnesses/canary/drift), Bash (Makefile).

**Spec:** docs/superpowers/specs/2026-10-22-vendor-0.4.0-schema-v3.md (brainstorm §5 design + the user's reversal: no v2 fallback; release only when v3 is served; acceptance-only change).

## Global Constraints

- **Accept v3 only.** `validateCatalog` must reject every schema_version other than 3, with reason `schema_version must be 3, got <actual JSON>`. No v2 (or older) acceptance anywhere in `src/`.
- **No change in what we show.** No rank, price, schedule, or display logic changes; the only visible-behavior change is: a stored/local catalog stamped v2 is now treated as stale and re-fetched/rebuilt, and the synthetic offline fallback stamps v3.
- **Release gate:** the plugin release only happens when the live remote (`https://canonical.github.io/model-compare/catalog.json`) serves `schema_version: 3`. The release gate script must fail closed otherwise.
- **Vendor pin is immutable here:** `vendor/model_compare.py` and `vendor/UPSTREAM.json` stay exactly as refreshed (upstream 0.4.0, commit `6f4b59f`); no local edits to the vendored script.
- **Commit style:** Conventional Commits, one commit per task (`feat:` / `test:` / `chore:` / `docs:`), no merge commits.
- **Quality bar before every commit:** `make test` (typecheck + lint + unit) exits 0. `make e2e` before the final task's commit.

## Review Focus

1. **v2 catalog present in storage** (user upgraded from an older plugin version, has a v2-stamped file in the data dir): expected — treated as stale, ignored, fresh v3 fetched and stored. Pinned by Task 4's "stored v2 document is re-fetched" test.
2. **Remote serves v2 (pre-upstream-deploy window):** expected — fetch rejected with the reason from Global Constraints; plugin surfaces the error, no stale-or-wrong-version data shown. Pinned by Task 3's "v2 document is rejected" test.
3. **Synthetic offline fallback when neither store nor network has data:** expected — the plugin shows the fallback models as today, since the shipped fallback doc now stamps v3 and passes the gate. Pinned by Task 4's "offline fallback stamps v3 and validates" test.
4. **Drift between vendored script and its pinned upstream commit** (someone re-vendors but forgets the pin file): expected — the drift check fails closed at publish/CI time. Pinned by Task 1's drift-check verification step.
5. **No-quality edge fixture must stay value-faithful to the v3 contract** (pool/rankings/schedules keys, schema_version 3): expected — the regenerated no-quality fixture carries `schema_version: 3` and the same value-based pins as today. Pinned by Task 2's pin-check step.
