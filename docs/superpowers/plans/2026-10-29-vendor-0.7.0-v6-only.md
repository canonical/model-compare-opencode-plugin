# Vendor 0.7.0 / Catalog Schema v6-Only Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Re-vendor upstream `model_compare.py` v0.7.0 and flip every plugin-side catalog-schema pin from v5 to v6, so the plugin accepts only the v6 contract (quality = best measured selectable depth) and never serves v5-era cached documents under v6 semantics.

**Architecture:** Upstream 0.7.0 changed catalog *semantics*, not shape: `quality`/`quality_effort` now mean the AA index/effort at the model's best measured selectable depth (may differ from `default_effort`); envelope and per-model fields are unchanged. The flip is therefore mechanical except for one real design decision: stored v5-era doc-cache records carry `qualityEffort` (since v5), so they round-trip through `validateStoredCatalog` and would mix v5 default-effort scores with v6 best-selectable-depth semantics. The fix is a doc-cache record version bump (`v: 1` → `v: 2`), which turns every pre-upgrade cached catalog into a cache miss; pin records stay `v: 1` and survive. Order follows the v0.4.0 precedent: re-vendor → record fixture + re-point SOURCE (no regeneration) → one atomic gate flip → regenerate no-quality exactly once → cache-version bump → docs/gates → release bump.

**Tech Stack:** TypeScript + vitest (plugin), Python 3 (vendored script), Node scripts for canary/drift/vendor sync.

**Spec:** upstream `CHANGELOG.md` §0.7.0 (sibling clone `../model-compare/CHANGELOG.md` — relative to the MAIN plugin checkout root, i.e. `~/git/gh/rkratky/model-compare/CHANGELOG.md`, not relative to this worktree, where `../` is `.worktrees/`; lines 8–32; released 2026-10-28, tag `v0.7.0`, commit `4b47c434c861fd2c1b64de9b56b1b8f3bc98070a`) + the plugin's catalog contract (design doc `docs/superpowers/specs/2026-10-08-model-compare-opencode-plugin-design.md` §5). Worktree: `.worktrees/vendor-0.7.0-v6-only` (branch `vendor-0.7.0-v6-only`, baseline: typecheck + 508 passed / 13 skipped).

## Global Constraints

- The plugin accepts exactly ONE catalog schema: v6 only. `validateCatalog` reason string: `schema_version must be 6, got <JSON.stringify(actual)>` (exact style of the current v5 string).
- All v5→v6 contract pins flip in ONE atomic commit (Task 3): gate, fallback stamp, canary `EXPECTED_SCHEMA_VERSION`, harness stub, every test fixture reference/stamp, old fixture deleted, no-quality regenerated.
- `fixtures/catalog-no-quality.json` is regenerated by running `scripts/make-no-quality-fixture.py` exactly ONCE, AFTER the gate flip; before that, Task 2 re-points `SOURCE` only (never runs it) — the v0.4.0 Ruling-3 ordering.
- `vendor/` changes only via `node scripts/sync-vendor.mjs v0.7.0` (fetches at the tag's resolved commit; re-pins `vendor/UPSTREAM.json`; sha256 recorded). The script is never hand-edited.
- `fixtures/catalog-v0.7.0.json` is recorded from an unmodified run of `python3 vendor/model_compare.py --catalog` — never hand-edited. NOTE: a quality-hydration failure does NOT fail the run — if the live remote still serves v5, upstream 0.7.0 warns `published catalog schema v5, expected 6; skipping hydration` and exits 0 with a quality-less (but schema-valid) catalog. The Step 2 pin check's scored-model assertion is the detector; if it trips, re-run — never hand-edit the fixture.
- Recorded-fixture pin check (same spirit as v0.4.0): `schema_version == 6`, non-empty `models`, non-empty `rankings.{balanced,price,quality}`, non-empty `pool` and `schedules`, AND at least one scored model (a `models[]` entry with non-null `quality` and a non-empty string `quality_effort`) — the last assertion is what fails loud on silent hydration degradation.
- Line numbers below are from HEAD `16c2108`; if drifted, grep-and-adjust (ledger precedent) — the pin is the content, not the line.
- The stored-doc invariant (design §7.9): a record the current plugin cannot fully validate is a cache miss, never a stale serve and never an exception.

## Review Focus

- **v5-era cached catalog served as v6** — after the gate flip a stored v5 record carries `qualityEffort`, round-trips the rebuilt stamp, and would serve default-effort scores under best-selectable-depth semantics. Expect: it is discarded as a cache miss (doc-cache `v: 2`). Pinned: Task 4 Step 1's new test.
- **`quality_effort` ≠ `default_effort` alias pinning** — the v6 scored depth may be a non-default effort (e.g. `deepseek/deepseek-v4.1-flash-1017` scores at `max`). Expect: `reasoningEffortFor` returns exactly the scored effort and the body pins `reasoning: { effort }` (upstream changelog's named plugin contract). Pinned: Task 3 Step 6's new fixture-derived test.
- **Roll-back/deploy skew: live remote still serving v5** — the release gate must fail closed. Expect: `checkCanary` reason `schema_version is 5, expected 6`, exit 1. Pinned: Task 3 Step 6 (canary.test.mjs wrong-version test flipped to seed v5).
- **Live remote already serving v6 at release time** — upstream published v0.7.0 on 2026-10-29; the gate only passes against the live v6 remote. Pinned: Task 6 Step 4 verification.
- **Hand-edited stored record with `qualityEffort` stripped** — still rejected (defense in depth), now independent of the version bump. Pinned: existing `rejects a pre-v5 stored projection` test kept (comment updated, Task 4).
